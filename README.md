# link-monitor

Моніторинг розміщених посилань для SEO-аутрічу.

**Проблема.** Аутрічер домовився і заплатив за лінк, а через місяць його тихо знімають, роблять `nofollow` або закривають сторінку від індексу. Руками 500 донорів ніхто щотижня не перевіряє, і гроші за лінкбілдинг витікають непомітно.

**Що робить.** Бере список розміщених посилань (CSV з Google Sheets або CRM), обходить сторінки-донори і перевіряє кожен лінк. У Telegram пише **тільки про зміни**: що злетіло, хто з аутрічерів розміщував і скільки грошей під ризиком.

```
🔴 Проблеми з посиланнями: 7 · під ризиком $750

🔴 сторінку-донор видалили (404/410)
донор: https://donor.example/best-casinos-2026
ціль: https://our-site.example/reviews/best-bonuses/
Оля · ціна $140 · розміщено 2026-10-01

🔴 лінк зник зі сторінки
донор: https://blog.example/slots-guide
ціль: https://our-site.example/reviews/best-bonuses/
Іра · ціна $100 · розміщено 2026-10-01
```

## Швидкий старт

Потрібен Node.js 22.19+.

```bash
npm install
npm run demo     # без інтернету: локальний «донор» з усіма поломками, видно весь цикл за 10 с
npm test         # 29 тестів, справжні HTTP-запити до локального сервера і через локальний проксі
npm start        # бойовий запуск по data/links.csv
```

## Що перевіряє

| Статус | Що сталось |
|---|---|
| ✅ `OK` | лінк на місці, dofollow, анкор збігається |
| 🟡 `ANCHOR_CHANGED` | лінк є, але анкор змінили |
| 🟡 `URL_CHANGED` | лінк веде на іншу сторінку нашого сайту (наприклад, на головну) |
| 🟠 `NOFOLLOW` | додали `nofollow` / `sponsored` / `ugc` (або meta robots nofollow на всю сторінку) |
| 🟠 `NOINDEX` | сторінку закрили від індексу (`meta robots` або заголовок `X-Robots-Tag`) |
| 🔴 `MISSING` | лінка на сторінці більше нема |
| 🔴 `GONE` | сторінку-донор видалили (404/410) |
| ⛔ `BLOCKED` | нас не пустили: капча, Cloudflare, 403. **Це не «лінк зник»** |
| ⚠️ `ERROR` | таймаут, мережа, 5xx після всіх повторів |

Додатково в нотатках: редірект сторінки-донора, `canonical` на іншу сторінку, кілька наших лінків на одній сторінці.

## Де воно зламається і що я з цим зробив

Найцікавіша частина. Скрипт, який «відкриває сторінку і шукає лінк», пишеться за годину. Складність у тому, щоб він не брехав і не банився.

| Що піде не так | Наслідок без захисту | Що зроблено |
|---|---|---|
| Сайт віддав капчу / Cloudflare замість сторінки | Хибний алерт «лінк зник», аутрічер іде сваритись з вебмайстром | Окремий статус `BLOCKED`. Заглушку антибота розпізнаю за заголовком і маркерами челенджу. Звичайна reCAPTCHA у формі коментарів **не** вважається капчею (є тест) |
| Сайт ліг на 10 хвилин | Хибний алерт по всіх лінках домену | Алерт про проблему лише після `confirmRuns` (2) запусків поспіль. `BLOCKED`/`ERROR` не перезаписують останній відомий статус. Після 3 невдач поспіль приходить окреме «глянь руками» |
| 50 лінків на одному домені → бан IP | Половина перевірок `BLOCKED` | Ліміт запитів на домен (`perHostDelayMs` + випадковий розкид). Різні домени йдуть паралельно, один домен завжди послідовно |
| 429 Too Many Requests | Довбемо далі, бан посилюється | Чекаю стільки, скільки просить `Retry-After` (секунди або дата). Якщо просять більше `maxRetryAfterMs`, здаюсь і ставлю `BLOCKED` |
| Мертвий або забанений проксі | Усі запити через нього падають | Ротація проксі. Після `proxyMaxFails` помилок поспіль проксі вимикається до кінця запуску. На капчі повтор іде вже через інший проксі, без проксі повтор з того ж IP не робиться |
| Пароль проксі в логах | Витік доступів у чат / CI | У логах тільки `host:port` (є тест) |
| Таймаути, обриви з'єднання | Один повислий сайт гальмує все | Таймаут на запит, повтори з експоненційною паузою, помилка одного лінка не валить прогін |
| `http` / `www` / `utm` / слеш у кінці / %-кодування кирилиці | «Лінк зник», хоча він на місці | Нормалізація URL перед порівнянням. Змістовні параметри (`?ref=`) не відкидаються |
| Старий сайт у `windows-1251` | Анкор кракозябрами → хибний `ANCHOR_CHANGED` | Кодування з заголовка або `<meta charset>`, тест на cp1251 |
| Гігантська сторінка або файл | Падіння по пам'яті | Читаю не більше `maxBytes` (5 МБ) |
| На одній сторінці кілька наших лінків | Зайві запити до того самого донора | Сторінка качається один раз, перевіряються всі лінки на ній |
| Telegram недоступний у момент алерту | Стан збережено як «вже повідомили», алерт загублено назавжди | Якщо Telegram не прийняв, стан не зберігається, наступний запуск надішле ще раз (є тест) |
| Обрив процесу посеред запису стану | Битий JSON, наступного разу всі алерти по новій | Запис атомарний (`tmp` + `rename`). Якщо файл таки битий, копія в `.broken`, старт з нуля без падіння |
| Щоденний спам «усе ок» по 500 лінках | Канал мютять, справжній алерт ніхто не бачить | Пишу тільки про зміни: нове злетіло / відновилось / не можу перевірити |

## Формат вхідного файлу

`data/links.csv` (приклад у `data/links.example.csv`). Роздільник `,` або `;` визначається сам, тож підійде і вивантаження з укр. Excel.

| Колонка | Обовʼязкова | Що це |
|---|---|---|
| `donor_url` | так | сторінка, де розміщено лінк |
| `target_url` | так | куди має вести лінк |
| `anchor` | ні | очікуваний анкор; порожньо = не перевіряти |
| `outreacher` | ні | хто розміщував, для алерту |
| `price` | ні | `$120`, `1500 грн`; сумується в «під ризиком» |
| `placed_at` | ні | дата розміщення |

Дублі пар «донор → ціль» і криві URL пропускаються з попередженням, прогін не падає.

## Налаштування

`config/default.json`, або свій файл через `--config=config/my.json`.

| Параметр | За замовчуванням | Що робить |
|---|---|---|
| `concurrency` | 4 | скільки доменів перевіряти паралельно |
| `perHostDelayMs` / `jitterMs` | 3000 / 1500 | пауза між запитами на один домен + випадковий розкид |
| `timeoutMs` | 15000 | таймаут одного запиту |
| `retries` / `retryBaseMs` | 2 / 2000 | повтори і база експоненційної паузи |
| `maxRetryAfterMs` | 60000 | більше чекати на 429 не будемо |
| `maxBytes` | 5000000 | ліміт розміру сторінки |
| `proxyMaxFails` | 3 | після скількох помилок поспіль вимикати проксі |
| `confirmRuns` | 2 | скільки запусків поспіль має підтвердити проблему до алерту |
| `unknownAlertAfter` | 3 | після скількох `BLOCKED`/`ERROR` поспіль просити перевірити руками |

Секрети в `.env` (у git не потрапляє):

```
TELEGRAM_BOT_TOKEN=...      # без нього алерт друкується в консоль
TELEGRAM_CHAT_ID=...
PROXIES=http://user:pass@host:port,http://user:pass@host2:port
```

Проксі можна також класти по одному в рядку в `config/proxies.txt`.

## Запуск по розкладу

Раз на день cron або systemd-таймером на сервері:

```
0 9 * * *  cd /opt/link-monitor && npm start >> logs/monitor.log 2>&1
```

Кожен запуск кладе повний CSV-звіт у `data/out/` (відкривається в Excel і Google Sheets), стан між запусками живе в `data/state.json`.

## Чесні обмеження і що далі

- **Лінки, які вставляє JavaScript**, у сирому HTML не видно, тож буде `MISSING`. Для таких доменів наступний крок: позначка в CSV + перевірка через Playwright тільки для них, бо headless-браузер на всі 500 донорів дорогий.
- **Індексацію сторінки-донора в Google** не перевіряю. Парсити видачу Google = капчі й бани. Правильний шлях: SERP API (DataForSEO, Serper) або Search Console API.
- Невдачі проксі рахуються глобально, не по кожному сайту окремо: проксі, забанений одним суворим сайтом, але робочий для інших, скидає лічильник на першому успіху.
- Вхід поки CSV. Наступний крок: читати й писати статуси прямо в Google Sheets / CRM аутрічерів, щоб статус лінка був видно біля рядка з оплатою.
